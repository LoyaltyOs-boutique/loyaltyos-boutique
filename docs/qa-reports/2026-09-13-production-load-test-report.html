Production Backend Load Test — Concurrency Ceiling

A ramped, mixed-usage load test run directly against the live production Convex deployment to find the real concurrency ceiling — not a single-endpoint hammer test — with hard safety guards against causing an actual outage.

Method

What was run

A standalone Node.js script (load-tests/mixed-load-test.mjs, since discarded — findings preserved here) used ConvexHttpClient pointed at the production deployment. It ramped through five concurrency levels — 50, 100, 250, 500, 1000 — each running virtual users for a fixed window. Each virtual user randomly picked one action, weighted ~85% read / ~15% write:

  • Reads (~85%): getLookbookById, getCatalogueItemById, getSettings, getCustomers (via one reused merchant session token, not re-logging-in per call)
  • Writes (~15%): createOrder, createReview — every write tied to one of 3 customer records tagged LOADTEST_2026_, so results were fully traceable and cleanly removable afterward
Safety design: a soft-stop rule halted the ramp after any level with >10% failures or p95 latency >5s; a hard-stop rule would have aborted the entire script immediately if 100% of requests — including safe read-only calls — failed for 5+ consecutive seconds, signalling a possible full outage rather than normal load. Neither rate limiters nor any other safety mechanism was bypassed to make the test "pass."

Analysis

Honest read: genuine capacity, or rate-limiter artifact?

Mostly genuine saturation, with one real caveat about the test harness itself:

  • Only 12 of level 250's failures were rate-limited, all from createReview's documented 20/hour-per-customer limiter — exactly matching the tagged test customers' review counts. createCustomer's limiter never fired. Rate-limited calls fail fast, so they don't explain the latency spike either.
  • The p95/p99 jump at level 250 (8.8s / 11.3s, up from ~1.6s / 2.5s at 50/100) affected the unthrottled 85% read traffic too — getSettings, getLookbookById, getCatalogueItemById, getCustomers all degraded together. That points at real saturation, not a limiter.
  • Caveat: ConvexHttpClient opens a fresh HTTPS connection per call rather than reusing a persistent socket. Part of the observed ceiling may reflect this single Node process's own connection fan-out rather than Convex's true backend limit. A more conclusive number would need ConvexClient (WebSocket) or multiple worker processes to isolate "Convex is the bottleneck" from "the test harness is the bottleneck."

Practical takeaway

The production backend held up cleanly through 100 concurrent mixed-usage virtual users with no failures and sub-2.5s p95 latency. At 250 concurrent, latency degraded sharply (p95 nearly 9 seconds) even though the failure rate stayed low — this is the practical ceiling observed today, not a confirmed hard limit, and not yet separated from the test client's own connection behavior.

Data hygiene

Test data — created and fully removed

3 customers (LOADTEST_2026_Customer_1/2/3), 34 orders, and 15 reviews were created during the run, all tagged and logged to load-tests/created-ids.json as they were created. A follow-up cleanup task deleted all 52 records via a temporary, identity-verified Convex mutation (fetched and tag-matched each record before deleting, zero skipped/mismatched), then confirmed zero remained via direct ctx.db.get lookups on every id. The temporary cleanup mutation and created-ids.json were both removed afterward. No pre-existing customer, order, or review data was touched.

Disposition

Script discarded

The script (load-tests/mixed-load-test.mjs) has been deleted from the working tree now that its findings are captured in this report. It was never committed to git. If a repeat load test is needed in future, this report documents the method well enough to rebuild it — or a future version should use ConvexClient (WebSocket) instead of ConvexHttpClient to remove the connection-fan-out caveat noted above.
