# LoyaltyOS Boutique — AI Automation Architecture (Gemini Phase)
Design doc — overall architecture, covers all 3 features

## Goal
Use Gemini to help the merchant scale personalization (AI-generated WhatsApp message drafts, AI-ranked/customized lookbooks, virtual events) without ever weakening the existing security guard or the "nothing auto-sends without a manual approve-click" rule that was re-audited and confirmed CLOSED/INTACT on 2026-09-03.

## Core principle (non-negotiable, inherited from existing audited architecture)
AI only ever *drafts* or *ranks*. It never calls sendWhatsAppTemplateMessage directly, never bypasses requireMerchantSession, never bypasses the whatsapp_consent gate, and never writes to message_actions itself. Every AI output lands in a new "draft" state that a human merchant must review and explicitly approve — exactly the same shape as the existing Approve & Send flow in Customers.jsx.

## 1. Gemini integration point (new file: convex/ai.ts)
- One guarded Convex action (actions only, since it needs fetch — mirrors the existing pattern in whatsapp.ts) per AI task: generateMessageDraft, generateLookbookRanking (virtual events don't need Gemini, see §4).
- All calls go through a shared internal helper that calls the Gemini API with a scoped prompt + the specific customer's non-sensitive context (name, tier, occasion type, last-purchase tags — never staff_notes, never measurements, never magic_token).
- API key stored as a Convex env var (GEMINI_API_KEY), never hardcoded in src/. Until this env var is set, every AI action must fail gracefully (caught, logged, falls back to the plain hardcoded template) — the app must work exactly as it does today with zero key configured, and light up automatically the moment a real GEMINI_API_KEY is added via `npx convex env set GEMINI_API_KEY <value>`, with no further code changes needed.
- On any Gemini failure/timeout: same fallback philosophy as WhatsApp Cloud API → fall back to the existing plain hardcoded template text (never block the merchant's flow).

## 2. Feature A — AI-drafted WhatsApp messages
- New table ai_message_drafts: { customer_id, occasion, occasion_date, draft_text, generated_at, status: "pending" | "used" | "discarded" }.
- New Convex scheduled function (crons.ts, first legitimate use of cron in this project) runs once daily: for tomorrow's birthdays/anniversaries (reusing existing getUpcomingBirthdays/getUpcomingAnniversaries queries), call generateMessageDraft for each, insert into ai_message_drafts. This job only writes drafts — it has zero access to sendWhatsAppTemplateMessage or recordMessageAction.
- Customers.jsx's existing "Birthdays tomorrow"/"Anniversaries tomorrow" tabs get a new optional field showing the AI draft text (editable textarea) instead of the static template — merchant can edit before clicking the same existing "Approve & Send" button, which still runs through the same guarded ApprovalModal.approve() → sendWhatsAppTemplateMessage → recordMessageAction chain, unchanged.

## 3. Feature B — AI-customized lookbooks
- New field on lookbooks (or a new table ai_lookbook_rankings — decide whichever is less invasive to Ma'am's existing schema at build time): stores a Gemini-generated ordering/highlight-tags based on that customer's purchase history + catalogue tags.
- Regenerated by a Convex internalAction triggered right after createOrder succeeds (event-driven, not cron) — so a purchase updates that one customer's ranking, not a blanket nightly job.
- Lookbook.jsx/PublicLookbook.jsx (approved-flow files) read the ranking if present and reorder catalogue items for display; if absent or stale, falls back to the existing default order — purely additive, non-breaking.

## 4. Feature C — Virtual events (VVIP-gated)
- No Gemini needed here — this is pure CRUD + access-control, same pattern as existing magic-link auth.
- New table events: { merchant_id, designer_name, event_datetime, vvip_only: boolean, description }.
- New field on users: vvip: v.optional(v.boolean()) (set in Customer Onboarding).
- New guarded Convex functions in convex/events.ts: createEvent, getEvents, deleteEvent (merchant-only, guarded).
- Public function getEventAccess(customer_token, event_id): returns "locked" until event_datetime - 5min, else returns the real join link — reuses the existing validateMagicToken pattern for customer identity, never a new auth mechanism.
- Sending the event link to customers reuses the exact same guarded WhatsApp approve-flow as Feature A — no new send path.

## 5. What stays untouched (STRICT, carried into every build prompt from here on)
convex/auth.ts, requireMerchantSession, the whatsapp_consent gate, recordMessageAction's idempotency check, and the "only a manual Approve click calls send" rule — none of these change for any AI feature. Any AI feature that would require touching these needs explicit ASK-BEFORE-EDIT approval, same as Ma'am's protected UI files.

## 6. Build order (once this spec is approved/saved)
Phase A — schema + convex/ai.ts plumbing + GEMINI_API_KEY env-var wiring only, feature-flagged off, no UI (this phase alone must leave the app fully working with the key unset, and fully functional the moment the key is set — no additional code changes needed after that). Phase B — Feature A (WhatsApp drafts). Phase C — Feature B (AI lookbooks). Phase D — Feature C (virtual events). Each phase = its own branch, build, test, team-review, merge — same discipline as Task 1.

## 7. Scalability Principles (backend must remain vertically and horizontally scalable)
Convex's own infrastructure already scales horizontally (function invocations) and vertically (managed compute) without any app-level configuration — that layer is not something this codebase controls or needs to. What this codebase is responsible for is not undermining that scaling with schema/query patterns that get slower as data grows. Every AI feature (and the Phase 0 prerequisite fixes) follow these rules:
- No full-table scans: every query used by an AI feature must go through an index (matches Phase 0's fixes to getCustomers, getTodayOrders/getTodaySummary, getUpcomingBirthdays/getUpcomingAnniversaries) — AI draft-generation reuses those same indexed queries, never re-scans the full users/orders table itself.
- No single hot document: AI-related data (drafts, lookbook rankings, events) is stored as one row per customer/order/event, never aggregated into one shared settings-style document that every write would contend on.
- Batched, rate-limited AI calls: the daily draft-generation cron and the per-order lookbook-ranking trigger call Gemini in small batches (e.g. per occasion-day, per single order) with a request-rate cap, so cost and latency stay flat as the customer count grows from tens to 1000+, rather than scaling linearly (or worse) with every customer.
- Every new table (ai_message_drafts, ai_lookbook_rankings or equivalent, events) is created with the indexes its actual query patterns need from day one, not added retroactively after a slowdown is found.
- Stateless guarded actions: all new Gemini-calling functions are Convex actions/mutations that take no in-memory state between calls (matches the existing requireMerchantSession pattern) — safe to run any number of them in parallel as load grows.
- This section's rules apply to Phases 1-5 equally; Phase 0's four fixes are the concrete first application of the same principle to the pre-existing code.
