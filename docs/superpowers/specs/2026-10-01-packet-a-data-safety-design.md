# Packet A: data safety fixes from the tab audit

## Goal
Stop silent data problems found in the merchant tab audit, without touching any protected UI file: pieces added to Current catalogue must not depend on whichever lookbook is newest; onboarding must never create a local-only phantom customer after the real customer was saved; event dispatch must never message soft-deleted customers; new customers and lookbooks must appear in the dropdowns without a reload.

## Evidence (design audit on fix/tab-audit at d79f1ee)
src/lib/db.js addCatalogueItem fills a missing lookbook_id with getLookbooks()[0] (newest by creation), so Manual Entry with Current catalogue, CSV import and Instagram import attach pieces to the newest lookbook. All 7 active pieces are attached to the PDF lookbook "Pdf LookBook". "Current catalogue" (value all) in Catalogue.jsx shows all pieces of every lookbook, and getCustomerCatalogue returns pieces of every lookbook regardless of kind. kind "catalogue" is already allowed by the schema; no catalogue-kind lookbook exists. The selector lists in Catalogue.jsx:168 and Campaigns.jsx:54 only hide kind pdf. deleteLookbook has no server-side guard. onboardCustomerRemote returns createLocalCustomer at db.js:2873 and 2894 after createCustomer already succeeded, and Onboarding.jsx and Join.jsx show success because the fallback has no error field. getDispatchRecipientsInternal in convex/events.ts has no is_deleted filter. selectorCache.customers is never cleared and selectorCache.lookbooksSelector is cleared only by deleteLookbook. Moving a piece only needs a patch of catalogue_items.lookbook_id; no other table stores a piece's lookbook id.

## Decisions (approved by the user)
1. Home lookbook: one lookbook with kind "catalogue", title "Current catalogue", source "manual", created by the server the first time it is needed. Its pieces show under Current catalogue and on the customer lookbook exactly like any other pieces.
2. addCatalogueItem: lookbook_id becomes an optional argument. When it is given, behaviour is unchanged. When it is missing, the server finds the active catalogue-kind lookbook, creates it if none exists, and inserts the piece there, all in the same mutation. The schema does not change (lookbook_id stays required on the table).
3. getLookbooksForSelector hides kind "catalogue", so it never appears in the Lookbook Manager or Campaigns dropdowns. getLookbooks, getLookbookById and getCustomerCatalogue keep including it so its pieces load everywhere.
4. deleteLookbook refuses a kind "catalogue" lookbook with a clear error, on the server.
5. getDispatchRecipientsInternal skips users with is_deleted true, with an in-memory filter after the existing indexed read. No index change.
6. One-time data move (separate step, user approved the list): the 7 active pieces now under "Pdf LookBook" move to the home lookbook, with a dry run first, then the real run, then the temporary code is removed and redeployed. After the move, selecting "Pdf LookBook" in the dropdown shows no product pieces; Current catalogue and the customer lookbook still show all 7.
7. Frontend, src/lib/db.js only (separate step): addCatalogueItem stops guessing a lookbook and omits lookbook_id when none is chosen. onboardCustomerRemote returns { error: "Customer saved, but the magic link could not be created. Please try again." } instead of createLocalCustomer when createCustomer already succeeded and the link step or the local sync fails, on both the merchant and the /join path; the no-client and /join catch fallbacks stay unchanged (known, accepted). selectorCache.customers is cleared after a successful create or reactivate in onboardCustomerRemote, onboardCustomer and bulkCreateCustomers; selectorCache.lookbooksSelector is cleared after a successful createLookbook and uploadPdfLookbook.
8. No protected file changes: Catalogue.jsx, Campaigns.jsx, Onboarding.jsx, Join.jsx, Templates.jsx and every other page and component stay unedited. No CSS, schema, auth, lock or demo data changes.

## Test plan
Backend deploy with a clean TypeScript check; function-spec shows addCatalogueItem with an optional lookbook_id; requireMerchantSession call sites stay 62; auth.ts and schema.ts have no diff. After the move and the frontend step: a piece added to a designer lookbook shows in that lookbook, in Current catalogue and on the customer lookbook; a piece added to Current catalogue shows in Current catalogue and on the customer lookbook; the home lookbook never appears in any dropdown and cannot be deleted; a customer or lookbook created mid-session appears in the Campaigns, Lookbook Manager and Templates dropdowns without a reload; a failed link step shows the error message and creates no local customer; a soft-deleted customer is never an event recipient; build CSS stays 30.42 kB; all test data is cleaned up afterwards.
