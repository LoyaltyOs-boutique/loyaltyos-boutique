# Customer-Facing Catalogue Pipe — Design

**Problem:** Lookbook.jsx (the personal magic-link customer feed) has never had a real Convex-backed catalogue fetch, at any point in this repo's history (confirmed via full git-history audit, 2026-09-16). It only reads a local array populated exclusively by a merchant-session-gated hydration function. A real customer's own device always sees src/data/seed.js's hardcoded demo items, never live catalogue_items.

**Confirmed intended architecture** (per Saidul, 2026-09-16): "Current catalogue" is a single shared global catalogue — every merchant-added product should be visible to every customer, new or existing, with no per-customer filtering. The future AI "personalized lookbook" feature is only meant to customize ORDERING/ranking per customer, never visibility/access. A specific designer lookbook's own share-link (WhatsApp/copy-link) already works correctly via the existing, separate PublicLookbook.jsx flow and is out of scope here.

**Fix (this task, backend only):** add one new public Convex query, `getCustomerCatalogue`, in `convex/lookbooks.ts`.

- Args: `id` (string, the customer's Convex `_id` as a string) and `token` (string, their `magic_token`) — the exact same two values Lookbook.jsx already holds after a successful `validateMagicToken` call.
- Handler: re-validate the caller is a genuine, non-expired customer using the SAME lookup/expiry logic `validateMagicToken` (convex/auth.ts:296-319) already uses (`by_magic_token` index lookup, `role === "customer"` check, `String(customer._id) === id` check, 180-day expiry check) — do NOT weaken or duplicate divergent logic; extract/reuse the same checks. If validation fails, return `null` (never throw) — Lookbook.jsx's existing null-handling convention already treats a null/failed customer-auth result as "show nothing real, fall back to local state."
- If validation passes: collect ALL catalogue_items across ALL lookbooks regardless of kind (catalogue/designer/pdf all included — per the confirmed shared-global-catalogue architecture), using the exact same aggregation `hydrateCatalogue()` already does client-side (iterate every lookbook via `ctx.db.query("lookbooks").collect()`, then every catalogue_items row per lookbook via the `by_lookbook` index) — but do it server-side in this one query so a customer's browser gets the full list in one round-trip instead of the merchant-only multi-call pattern.
- Return shape: an array shaped identically to what `hydrateCatalogue()` already builds client-side (id/convexId, title, price already converted paise-to-INR, image_url, instagram_link, source, lookbook_id) — this exact shape match matters, because the frontend follow-up task will merge this directly into `state.catalogueItems`, and every existing read of that array (cart, likes, checkout) expects this shape unchanged.
- This query must NOT require or check any merchant session — it is customer-facing only, gated purely by the customer's own valid magic-link identity as described above.
