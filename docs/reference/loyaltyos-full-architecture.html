Part 1 · The big picture

One machine, four layers

Think of the system as a boutique with three shop-fronts and a back office. The shop-fronts are where people stand: the owner's dashboard, the client's private link, and WhatsApp. The back office is where the work happens — a careful clerk (the application) and a clever copywriter (the AI), both working from one filing cabinet (the database).

In plain words: the owner, the client and WhatsApp all talk to one front door (the API). Behind that door, a careful clerk does all the fact-finding and checking, and only passes a small, exact packet of facts to a clever copywriter who writes the nice words. The copywriter never opens the filing cabinet itself — which is the single biggest reason this system stays accurate, fast and cheap to run.
Part 2 · The one golden rule

The AI is given facts — never asked to find them

Every other design decision in this document flows from one rule. Understand this one line and the whole architecture makes sense.

R0The AI never searches, filters, or remembers. It only turns truth into words.All fact-finding is done by the application using the database. The AI receives a small, exact, pre-assembled packet of facts and returns words that fit around them. It is never the database, never the search engine, never the memory.
Why this rule exists — the three disasters it prevents: 1. Hallucination — if the AI must "find Meera's info", it can find the wrong client's info or invent missing details. Given facts, it cannot invent them. 2. Token blow-up — if the AI must "read the history", it must be fed the whole history every time. Given a small packet, it costs pennies. 3. Slowness — the AI call takes seconds; a database lookup takes a millisecond. The less the AI must do, the faster everything is.

Compare the two ways a birthday message could be made:

❌ The fragile way (AI as memory)✅ The stable way (this architecture)
Prompt the AI: "Look through the client history directory for Meera's record and write a birthday message." Application reads exact fields: name=Meera, nickname=Mimi, birthday=tomorrow, gift=500 pts, consent=yes.
AI reads (or guesses at) the files; may confabulate a wrong name or date. Template filled with real values: "Dear Mimi, … we've added 500 points…"
Every run re-reads the whole directory — slow and expensive. Only a tiny packet travels to the AI — fast and cheap.
In plain words: you would never ask a copywriter to also run the filing cabinet, because he might misfile or invent a document. Same here. The AI writes the nice words; the database holds the truth. They never trade jobs.
Part 3 · The data model

Your "folders and notes" — translated into a filing cabinet

Your idea of a client directory with sub-folders was the right shape. Here is that same idea, rebuilt on the correct foundation: one folder of fixed facts, one growing log of events, and one derived "note" per client that the AI is allowed to read.

3.1 The three pieces of every client's record

Your folder ideaBecomes thisWhat it holds
Onboarding folder clients table Identity, contact, birthday/anniversary, the three consent switches. Small, fixed, kept separate — exactly as you wanted.
Sub-folders that grow client_events log Every action a client takes (likes, reserves, buys, replies) — append-only, never edited, never deleted.
The "note" the AI reads client_profile_summary derived A short, current summary of taste, re-built from the log, carrying reasons. This is the ONLY history the AI ever sees.

3.2 The full data model, table by table

Every table below, with each field and — in plain words — why it exists. Fields marked append-only can be added to but never changed or deleted.

clients — the onboarding folder

Identity and fixed facts only. Kept deliberately small so no AI or query ever has to carry it around.

FieldWhy it exists (plain words)
client_id (PK, random)The "directory name" — an unguessable internal ID. Never shown to clients.
full_nameThe one, exact spelling of her name. The AI is never allowed to spell a name itself — it copies from here.
nicknameThe warm name you use ("Mimi"), filled into templates as a variable. Never guessed by the AI.
phone / whatsapp_idWhere messages go. Unique — one record per person.
birthday, anniversaryDates in columns, so "whose day is tomorrow" is one instant query — not a scan of folders.
consent_occasion / consent_marketing / stop_flagThe three separate switches (feature-doc P4). Checked at send time, every time.
tier, exclusive_flagStandard / Champagne / Noir, and membership of the ~2,000 exclusive list.
measurements (confidential)Stated at onboarding, kept confidential and blocked from the client link (feature-doc F2).

client_events — the growing history log append-only

The heart of the system. Every single thing that happens to a client becomes one row here. Nothing is ever edited or deleted — history is honest by construction.

FieldWhy it exists (plain words)
event_id (bigserial)The order in which things happened. This ordering is what makes the summary rebuildable.
client_id (FK)Which client this event belongs to — the "sub-folder" link.
event_typeA fixed label: like, reserve, purchase, open, reply, stop, consent_change, admin_correction, points_earned…
payload (JSON)The structured detail of the event — e.g. which piece was liked, what she replied. Structured, so it can be counted and filtered; never free prose.
created_atWhen it happened, down to the instant.
Why append-only? feature-doc G4 says "you cannot rewrite history." A database table with no update/delete permission makes that a physical fact, not a promise. (Compare: a folder of text files can be overwritten by anyone, by accident.)

client_profile_summary — the "note" the AI reads derived

Your best idea, made safe. A short summary of taste, re-built automatically from the event log. This is the only part of a client's history the AI is ever shown.

FieldWhy it exists (plain words)
client_idWhose note this is.
version, generated_atWhich "edition" this is, and when it was built — so we always know if it is fresh.
status (current / stale)If new events arrived since it was built, it is marked stale and re-built — never used while stale. This kills the "she loves pastels" hallucination.
taste: designers[], sizes[], colours[], price_bandThe conclusions — favourite designers, sizes, colours, usual spend.
reasons: fact → [event_ids]Every conclusion lists its source events — "two purchases, five likes." This keeps feature-doc P2 alive: no black boxes.
source_event_watermarkThe last event_id this summary has seen — so "is it stale?" is one comparison, not a re-scan.
Your correction always wins (feature-doc P3): when you hand-correct a taste fact, that correction is recorded as a special event and treated as stronger than any inference — so the rebuilt summary respects it forever, and the system never quietly reverts you.

pieces & lookbooks — the shelf

The catalogue the features draw from. One piece = one card with its own price, size, colour and stock.

FieldWhy it exists (plain words)
piece_idOne item card.
lookbook_id (FK), designer, collectionWhere the piece lives — "Sabyasachi" or "The Wedding Edit 2026".
price, size, colourPer-piece details. May be blank until you fill them; the reader never guesses (feature-doc F3).
stock_status (in_stock / sold_out / removed)The single source of honesty. A shared link shows "Sold out" live when this flips (your latest addition to F4).
image_urlPoints to the picture in object storage — not stored inside the database.

points_ledger append-only

Money, kept honest. Points are never stored as a single editable number — only as a list of additions and subtractions.

FieldWhy it exists (plain words)
entry_id, client_idOne line in one client's points history.
delta (+ / −)Points earned or spent. A purchase adds; a redemption subtracts; a birthday gift adds.
reason, referenceWhy (purchase / gift / redemption) and the linked order — so the balance is always explainable.
The balance is computed, not stored: "her balance" = the sum of all her deltas, calculated on demand. There is no number to edit or corrupt — the arithmetic is always right. (Feature-doc G4: this is the one thing you can never rewrite.)

messages — the outbox audited

Every outbound message lives one strict life: draft → approved → sent → delivered/read. No message exists without an approval record.

FieldWhy it exists (plain words)
message_idThe message.
template_id + filled valuesWhich template, and the exact facts that were filled in — so we can always replay "what was actually said."
status (draft→approved→sent→delivered/read)Where the message is in its life.
approved_by, approved_atWho approved, and when — feature-doc P1/G2, full traceability.
idempotency_key (unique)The physical guarantee of "each message only goes once" — the database refuses a duplicate. This is how "you can't double-send" is enforced.

The supporting tables

TableWhat it holds, and why
linksEach client's private link (unguessable token, active/revoked/expired). Revoking is instant (F2).
templatesYour fixed wording with variables — {name}, {nickname}, {gift_value}. The AI fills around them; the facts never come from the AI.
events (virtual)The trunk-show: teaser time, unlock time, end time, guest list.
sent_wishesWith a unique (client, occasion, year) key — the physical guarantee of "one wish per year."

audit_logWho changed what, when, and what it was before (feature-doc G4).
Part 4 · The six core flows

How the pieces move, step by step

Six flows cover almost everything the system does. In each, notice where the AI sits — and where it is deliberately kept out.

Flow 1 · Onboarding a client

  1. You enter name, nickname, phone, birthday, anniversary, and set the three consent switches. All of this lands in the clients table — the small, fixed folder.
  2. The system creates her private link token and her empty points ledger. No AI involved at all — nothing to generate or guess.
  3. Done. Her record is ready; the history log starts empty and will fill as she acts. Onboarding stays separate from history, exactly as you wanted — so it never costs tokens later.

Flow 2 · Recording a client action (the heart of the log)

  1. Meera taps ♥ on a Sabyasachi lehenga on her private link.
  2. One row is appended to client_events: {client: Meera, type: like, piece: #482, time: now}. Append-only — this row will exist forever, unedited.
  3. The summary is marked stale (its watermark is now behind the new event). It is not rebuilt immediately — that would be wasteful for a single tap.
  4. Later, quietly, the summary re-builds from the log, including this like and its reason. So the "note" always trails the truth, and is always honest about it.

Flow 3 · The birthday engine (your calendar idea, done right)

  1. A scheduled job runs each morning and asks one question: "whose birthday or anniversary is within the next 24 hours?" Because dates live in columns, this is one fast query — not a scan of folders.
  2. It filters out anyone whose occasion-consent is off, and anyone already wished this year (checked against the unique key). Consent and "once per year" are enforced here, by the database.
  3. For each remaining client it assembles a small packet: name, nickname, occasion, gift value, tone — and asks the AI to write the warm words around them. The AI only writes prose; the facts were handed to it.
  4. A reminder + draft appears on your dashboard — one day before. You edit if you like, then Approve & Send. Nothing is sent by the job. It only prepares (feature-doc P1).

Flow 4 · A custom lookbook suggestion

  1. You press "Suggest Lookbook" on Meera's page (or she asks on WhatsApp).
  2. The application filters the catalogue in SQL: in_stock AND size in her sizes AND price in her band AND designer in her favourites. This narrows thousands of pieces to a few dozen — done by the clerk, in milliseconds.
  3. It reads her summary (taste + reasons) — and if only 2 pieces survive, it says so honestly. No padding; feature-doc P5.
  4. The AI receives the ~20–40 survivors + her summary, and returns a ranking with a one-line reason per piece — the reasons are derived from the data, not invented.
  5. You review, adjust, approve. She receives her private link.

Flow 5 · Sharing a lookbook or piece

  1. You choose the lookbook or single piece, and copy the link — or use the WhatsApp button.
  2. Button path: a message is drafted from the template + variables; you edit and approve; it is sent once (unique key).
  3. Live honesty: if a piece sells out after sharing, the shared link's card flips to "Sold out" because it reads stock_status live — never a stale price. Your F4 addition, made automatic by pointing the link at the live field.

Flow 6 · A virtual event

  1. You create the event: pick the lookbook, set teaser/unlock/end times, choose guests.
  2. Invites draft and wait for your approval. Early birds see the teaser — with prices hidden by not sending them to the device until the unlock moment (P5).
  3. At the unlock hour, prices appear for everyone at once.
  4. Buy Now creates a real order (points appended to the ledger) — Book with Stylist creates a reserved order and alerts the stylist within a minute.
  5. After the window, the link closes gracefully; the dashboard shows what sold, live.
Part 5 · The AI layer

How the copywriter is kept honest

The AI is the only creative part of the system, so it is also the part that must be most tightly fenced. Four fences keep it safe.

Fence 1Constrained output.The AI must return its answer in a fixed shape (a small JSON schema) — never free-form text that might wander. If it cannot fit the shape, the request is rejected and retried.
Fence 2Facts are variables, not model output.Names, nicknames, dates, numbers, gift values are filled from the database into the template. The model writes only the connective warmth around them. It is structurally incapable of inventing a name.
Fence 3Validation + a safe fallback.Every draft passes checks (right name? no budget talk? within length?). If it fails, a pre-approved "safe classic" message is used instead — there is always something good to send (feature-doc P8).
Fence 4Human approval is the last gate.Nothing the AI writes reaches a client until you have read and approved it, and that approval is recorded. The AI suggests; you decide (feature-doc P1).
The learning boundary (feature-doc P3, made concrete): the system may learn from your edits to wording — how you phrase things — to sound more like you over time. It never learns from your edits to facts. A stated fact is treated as final, not as a training example. These two learnings live in two different places in the code, so one can never bleed into the other.
Part 6 · The four worries, answered

Tokens, hallucinations, speed, scale — each traced to a design choice

6.1 Token usage → small, exact packets

Every AI call receives a packet of a few hundred tokens — a summary and the needed variables — never a full history. Summaries are re-built only when data changes, not on every request. Onboarding facts are excluded from the AI entirely because they are already in the database as typed columns. Result: the AI is asked for ~300 tokens of context for a birthday message, ~1,500 for a lookbook suggestion — regardless of whether the client has 10 events or 10,000.

6.2 Hallucination → the AI never holds the truth

Because the AI is given facts (R0) and returns a constrained shape (Fence 1), and identifiers are variables (Fence 2), the two classic hallucination sources — searching and inventing — are removed. Stale-summary hallucination is removed by versioning and the stale flag. What remains is purely stylistic risk, and that is caught by validation and human approval.

6.3 Speed → everything is a lookup except the one thing that must be slow

A database lookup by client_id is ~1 millisecond; assembling a packet is ~10–50 ms; the AI call is 1–5 seconds. So speed is simply: minimise AI calls, and make each one tiny. Scheduled work (all morning birthday drafts) is batched into one job rather than N on-demand calls. Summaries are cached and reused until stale. The private link and dashboard reads are pure database reads — no AI in the request path at all.

6.4 Scale → correctness under concurrency, not raw size

A few thousand clients is a small database. What breaks a naive design is concurrency: two writes racing (a like vs a correction), a double-send under retry, an edited "history". This architecture meets each with a structural answer — transactions for atomic writes, unique keys for idempotency, append-only tables for immutability. Those are exactly the guarantees a folder-of-files cannot give.

Part 7 · Security & the law

DPDP compliance, built in — not bolted on

India's DPDP Act 2023 and Rules 2025 are fully in force (since 14 Nov 2025). The data model above already satisfies the main duties; here is the mapping.

DPDP dutyWhere this architecture satisfies it
Notice & consentThe three consent switches in clients, recorded at onboarding, re-checked at every send.
Right to access / correctEverything is a table the dashboard can read and update; corrections are logged (P3).
Right to erasureA client can be erased properly — her record and link removed; the event log supports a verified deletion flow.
Security safeguardsEncryption at rest and in transit, access control, masking of confidential fields (measurements), tokenised links.
Retention limitsPurpose-bound retention with automatic erasure after inactivity, while keeping the logs the law requires.
Breach notificationA prepared, practised process; the audit_log and event log give the "what was affected" answer quickly.
Data residency: client data is kept in an India region — simplest for compliance and for your clients' trust. Cross-border transfer rules under DPDP are changing; staying domestic sidesteps that entirely.
Part 8 · The technology stack

What each piece is — and why it was chosen

ComponentChoiceWhy (plain words)
DatabasePostgreSQLThe filing cabinet. Transactions, unique keys, JSON fields, append-only tables — every guarantee in this document maps to a Postgres feature. Free and battle-tested.
Backend applicationNode.js or Python (one language, kept small)The careful clerk. Ordinary, boring, reliable code that does retrieval, templates, validation, scheduling. Nothing exotic — exotic is where bugs hide.
AI modelA hosted LLM, called over an APIThe copywriter. Called only for prose and ranking, with a constrained output schema. A hosted model means no in-house AI infrastructure to run.
SchedulerA cron/queue job (e.g. in-app scheduler)Runs the morning occasion job. Simple, observable, idempotent.
ImagesObject storage (S3-compatible)Lookbook photos are files, so they live in file storage, not in the database — the database stores only a pointer.
WhatsAppWhatsApp Business API providerThe Studio number, with approved templates, separate from the Owner's number (feature-doc G1).
PaymentsUPI + card gatewayFor Buy Now at events; orders and the points ledger stay in sync.
Cache (optional)RedisSpeed for hot reads — the private link and dashboard. Optional at first; the database alone is enough to start.
Deliberately avoided: no exotic "vector database", no agent framework, no AI-as-database. Those tools are for searching unstructured text — this system does not search, it looks up. Keeping the stack boring is the whole point.
Part 9 · Growing & running it

Operations — what keeps it alive

Backups & recovery

Automated daily backups of the database and object storage, with a tested restore. Because the event log is append-only and everything else is re-derivable from it, a restore is always consistent.

Monitoring

Three things are watched at all times: is the scheduler running, are messages delivering, are summaries being re-built. These three catch most failures before a client ever notices.

Growing to 10×

At 10× clients, nothing structural changes — the same queries, indexes and tables scale linearly. The only growth items are: a queue for large sends (so they drip, not burst), and caching for the busiest reads. The architecture was chosen to not need rebuilding at 10×.

The off-switches

Every feature has an independent off-switch in settings (feature-doc G2). Operationally, this means a misbehaving feature can be stopped in seconds while the rest of the boutique keeps running — no redeploys, no panic.

How the build maps to this (unchanged): 1) clients + events + consent → 2) occasions scheduler + templates → 3) Studio WhatsApp + messages outbox → 4) catalog + private links → 5) summaries + suggestions → 6) events. Each stage is independently testable, and the launch gates in the Feature Document (v2.0, Part 5) verify the principles — consent live, approval recorded, ledger append-only, erasure works — which is what a public launch actually depends on.
